**Run method and reproducibility.** The working-tree compiler was checked with `cmake --build compiler/build --target delphi-compiler --parallel 8` and copied before the batch, so every row used the same binary. The checkout had uncommitted compiler changes; the Git commit alone does not identify this build. The binary SHA-256 is `447705decf4f9b51e079a33d8fa31021a0ba5da10cb0323eabe78019ffd54d5c`. The [metadata](../../results/micro-apps/20261020-100ms/metadata.json) records the checkout commit, tool versions, commands and timestamps; the [compiler diff](../../results/micro-apps/20261020-100ms/compiler.diff) records the working-tree changes captured at batch startup. The live build changed while this report was being prepared; these results describe the preserved binary.

Clang 21.1.0 generated 32-bit LLVM IR with `-m32 -std=c99 -O0 -g -fno-discard-value-names -Xclang -disable-O0-optnone -pthread -S -emit-llvm`. `-O0` avoids front-end optimization removing unused memory accesses such as the worker read in `value-barrier.c`; Delphi still performs its own preparation passes. Every generated module passed `opt -passes=verify -disable-output`. No executable benchmark was run and no source or compiler logic was changed for this experiment.

The host lacked 32-bit glibc development headers. Package `libc6-dev-i386=2.39-0ubuntu8.9` was downloaded and extracted into the run directory, with its include paths and the existing host multiarch headers supplied to Clang. No package was installed system-wide. A forced header declares `extern int __VERIFIER_nondet_int(void);` to make the existing no-argument calls have a consistent LLVM call type on i386; it supplies no body, input bound, memory-effect attribute or race assumption. The input remains nondeterministic and unresolved external calls remain conservative.

The analysis command for every module was:

```sh
results/micro-apps/20261020-100ms/delphi-compiler \
  --symbex-timeout-ms=100 \
  --input-timeout-ms=100 \
  --dump-unresolved=<file>.pairs.txt <file>.ll
```

The first 100 ms limit applies to each symbolic access-pair check; the second is the shared worker-input construction budget for the whole module. This is **not a 100 ms total-process deadline**: parsing, preparation, static analysis, repeated pair checks and output take additional time. Files ran sequentially with a separate 300 s process guard, which was never reached. No fixed-cohort assumptions or disabled-symbolic options were used.

The diagnostics show modeling limits beyond the requested budget. For example, [`atomic-gcc.c`'s pair dump](../../results/micro-apps/20261020-100ms/atomic-gcc.pairs.txt) contains three incomplete-summary pairs involving external nondeterministic/abort calls and one unresolved atomic self-pair. [`thread-join-array-const.c`](../../results/micro-apps/20261020-100ms/thread-join-array-const.pairs.txt) leaves all five pairs blocked by unsupported loops despite the source joining every handle. Raising a timeout alone is not established as a remedy by these results.
